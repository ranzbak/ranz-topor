# 30 — KiCad constraints on a curved-trace router

What KiCad allows, offers and limits, as it affects whether a TopoR-style router is feasible
as a KiCad plugin. Verified 2026-10-30 against KiCad `9.0` / `10.0` / `master` sources,
kicad-python 0.8.0 (KiCad API 10.0.6) and docs.kicad.org; UNVERIFIED where noted.

---

## 1. Can KiCad store the result? — Yes

- Copper tracks are **straight segments** and **circular arcs** (arcs since KiCad 6).
  An arc is stored as integer-nanometre **start, mid, end** points; KiCad recomputes centre
  and radius. No Bézier/spline tracks → any other curve must become arcs (biarcs,
  [22](../geometry/22-smoothness-and-biarcs.md)).
- Vias: through, blind, buried, micro.
- Teardrops (KiCad 7+) are generated by KiCad as special zones.
- KiCad's interactive router can edit and drag plugin-made arcs; shoving re-lays geometry in
  its own 45°/arc-corner style, so manual edits locally lose the any-angle shape (UNVERIFIED detail).
- File format change in KiCad 10: nets written **by name**, numeric net codes removed;
  KiCad 9 still uses numbers. The public format page is out of date.

## 2. Can a plugin read everything needed? — Mostly

Through the IPC API (`kicad-python`) a plugin can read: copper layer count and stackup,
footprints, pads with full padstack geometry (all shapes incl. custom; exact copper polygons
on request), nets, **netclasses** (clearance, track width, via sizes, diff-pair width/gap),
existing tracks/arcs/vias, zones and rule areas, Edge.Cuts outline.

**Gap — design rules:** in KiCad 10 the API has **no query for board minimums, custom rules
or the effective clearance between two items**. The legacy SWIG API offers only a per-item
"own clearance", also not pairwise. Consequences:

- Board minimums and netclasses must be read from the project file (`.kicad_pro`, JSON) and
  custom rules from `.kicad_dru`, parsed by the plugin.
- Pairwise clearance = conservative maximum of both items' values + margin; exactness is left
  to KiCad's DRC.
- No ratsnest/unrouted-connection query (UNVERIFIED): connections are derived from nets and
  existing copper connectivity.

## 3. Can a plugin write the result? — Yes

Tracks, arcs and vias can be created, updated and removed, grouped into one undoable commit.
Zones can be refilled through the API. Locked items can be detected and left alone.

## 4. Can the result be verified? — Yes, outside the API

- `kicad-cli pcb drc` with JSON output, optional zone refill, exit code 5 on violations;
  each violation lists the involved item UUIDs and positions → violations can be mapped back
  to individual connections for rip-up.
- DRC runs on a **saved** board file; in KiCad 9/10 the API cannot run DRC itself.

### 4.1 KiCad DRC as guide rails (not only a final gate)

Because the API gives no access to KiCad's rule engine (§2), `kicad-cli pcb drc` is the only
**exact** oracle for KiCad's rule semantics. It can steer the router, not just judge it:

| Use | How | Value |
|---|---|---|
| **Verify-and-repair loop** | Violation item UUIDs → generated connections → rip-up with raised history cost and/or a larger local margin, then reroute | Turns "approximately rule-aware" into "DRC-clean after iteration" |
| **Covers what the router cannot model** | Custom `.kicad_dru` conditions, `hole_clearance`, `edge_clearance`, `track_angle`, `diff_pair_gap`, `length`/`skew`, `via_count`, creepage, zone effects after refill | No need to re-implement KiCad's rule language |
| **Unrouted connections** | The report's `unconnected_items` lists what is still unrouted | Closes the "no ratsnest query" gap (§2) and measures completion |
| **Pre-flight check** | Run DRC on the board *before* routing: existing violations are excluded from blame; detect rules that will reject arcs (`track_angle`) | Clear attribution; early warning |
| **Margin calibration** | Where a parsed/approximated clearance proves too small, DRC failures reveal it; raise the margin locally for that netclass/rule | Learns effective clearances empirically |
| **Feedback in the editor** | The API has an `InjectDrcError` message (severity, text, position, items) to show markers for connections the router gave up on | User sees exactly what failed (wrapper availability UNVERIFIED) |

**Keeping the user's board untouched while iterating:** write candidate results into a
*temporary copy* of the board file and run `kicad-cli pcb drc --refill-zones --format json`
on that copy; commit to the live board through the API only once the result is clean (or
accepted). Whether the API's save-as switches the open document to the new path is
UNVERIFIED, so the copy is best produced outside the API.

**Limits:**
- Whole-board runs only, seconds each (≈ 2–20 s incl. refill, estimate) → once per
  rip-up *iteration*, never inside the inner search loop; the engine's own exact checks
  ([23](../geometry/23-distance-and-drc-checks.md)) remain the fast inner filter.
- Pass/fail per item pair: no "how far off" gradient beyond the reported actual vs required
  values in the description text.
- Use `--all-track-errors`, otherwise only the first error per track may be reported.
- Applies KiCad's `DRCEpsilon` (0.5 µm), so a clean report is not proof of margin.

### 4.2 Delegating post-processing to KiCad tools

Some clean-up KiCad already does well; the plugin can trigger it instead of re-implementing it.
Verified in KiCad 10 source (`pcbnew/tools/pcb_actions.cpp`): the actions
`pcbnew.GlobalEdit.cleanupTracksAndVias` ("Cleanup Tracks & Vias…": merge collinear segments,
remove redundant/dangling vias and tracks, duplicates, tracks inside pads, shorts) and
`pcbnew.GlobalEdit.editTeardrops` ("Edit Teardrops…") exist and can be invoked from an IPC
plugin through the API's run-action call. Both open their **dialog** (the names end in "…"),
so this is semi-automatic: the plugin opens the dialog after routing, the user confirms.
Not available headless: no SWIG binding (no `TRACKS_CLEANER` in `pcbnew` 10.0.8, checked
locally) and no `kicad-cli` command.

Policy:
- The engine still emits clean geometry itself (no collinear duplicates, shared endpoints,
  arcs never split) — KiCad cleanup is a convenience, not a correctness step, and must not be
  needed for DRC-clean output.
- Offer "Run KiCad cleanup" and "Add teardrops" as optional post-route steps (user toggles),
  after zone refill, before the final DRC.
- Caution: cleanup works board-wide unless limited to a selection (selection-only option
  UNVERIFIED); "delete dangling tracks" would remove **partial routes**
  (option `partial_routes`) — warn or skip that checkbox when partial routes are on.
- Teardrops: closes the earlier open point (no API to *generate* teardrops) — generation goes
  through this action/dialog.

## 5. Design-rule facts that shape the router

| Rule / setting | Effect on a curved router |
|---|---|
| Netclass clearance, track width, via size/drill, diff-pair width/gap | Inputs to obstacle inflation and stack radii. |
| Custom rules (`.kicad_dru`): `clearance`, `hole_clearance`, `edge_clearance`, `hole_to_hole`, `track_width`, `via_diameter`, `annular_width`, `diff_pair_gap`, `length`, `skew`, `disallow`… | Conditions are expressions over item pairs (A/B) → cannot be evaluated exactly without re-implementing KiCad's rule language; parse common cases, be conservative otherwise. |
| **`track_angle`, `track_segment_length`** constraints | A user rule restricting angles **will flag any-angle and arc geometry** — must be detected and reported up front. |
| Rule areas with `disallow track/via` | Hard obstacles. |
| `DRCEpsilon` = 0.5 µm, `ExtraFillMargin` = 0.5 µm, arc polygonisation `ARC_HIGH_DEF` = 5 µm (verified in source) | Routing exactly at minimum clearance is unsafe; a **5–10 µm margin** is needed. |
| Arc-DRC history: false errors at exact clearance (#8234), arc-to-arc rounding fix (Oct 2024), arc diff-pair distance issue in 9.0.1 (#20636) | Arc DRC has had edge cases recently; keep margins, treat KiCad DRC as the final judge. |
| Integer-nm arc storage; centre recomputed from 3 rounded points | Small/flat arcs drift; see [23 §4](../geometry/23-distance-and-drc-checks.md#4-quantisation-to-integer-nanometres). |

### 5.1 Missing or default track widths

Many designs never set widths per netclass: every net sits in `Default`, and wide
power/high-current tracks were chosen by hand while routing (from the board's
"pre-defined track widths" list). A router reading only netclasses would then route power
nets at signal width — a working-PCB failure that DRC does **not** catch (it only checks
minimums). Width must therefore be resolved, in this order:

| Source | Use |
|---|---|
| Custom rule `track_width` (opt/min) matching the net | Explicit intent; highest precedence |
| Impedance target (netclass/profile + stackup) → computed width/gap per layer, see [26](../geometry/26-impedance-controlled-geometry.md) | Per-layer microstrip/stripline solve; beats plain netclass width |
| Netclass width, if the net is in a non-`Default` netclass | Explicit intent |
| Existing routed copper on that net (before ripping), e.g. median width | Recovers hand-chosen widths on already-routed boards |
| Plugin settings table (net / netclass / pattern → width or current) | User fills gaps; width from current via IPC-2152-style sizing (KiCad's calculator tool covers this, not exposed via API) |
| `Default` netclass width | Fallback for signal nets only |

Board minimum track width and manufacturer limits are a floor, never a choice. A
**pre-flight report** should list nets that would fall back to `Default` but look like power
(names like `VCC`, `+5V`, `VBAT`, `GND` without a plane, or many pads, or wide existing
copper), and ask the user before routing. The same resolution applies to via size/drill
for power nets (via count or size for current). Resolved widths also drive the priority
tier for wide power traces ([12 §3.1](../topology/12-sketch-generation.md#31-net-priority-signal-importance)).

### 5.2 Manufacturer baseline when the design sets nothing

Precedence for every constraint: **custom rule → netclass → board-setup constraint →
manufacturer profile**. The profile only fills gaps; it never relaxes a stricter design value.
Default profile: **JLCPCB standard rigid, 1 oz copper** (retrieved 2026-10-30 from
https://jlcpcb.com/capabilities/Capabilities). Router defaults use the *recommended* values
and stay above the minimums, because routing exactly at a fab minimum leaves no tolerance
(track width ±20%, hole position ±0.075 mm).

| Constraint | Fab minimum (1–2 L / 4+ L) | Router default (proposal) |
|---|---|---|
| Track width / spacing, 1 oz | 0.10 / 0.10 mm · 0.09 / 0.09 mm | width 0.20 mm, clearance 0.15 mm |
| Track width / spacing, 2 oz | 0.16 / 0.16 mm · 0.15 / 0.15 mm | +50% over 1 oz defaults |
| Pad to track | 0.10 mm (0.09 mm locally at BGA pads) | 0.15 mm |
| SMD pad to pad, different nets | 0.15 mm | — (placement, not routing) |
| Via drill / diameter | 0.15 / 0.25 mm; drill ≥ 0.2 mm recommended; diameter ≥ drill + 0.1 (0.15 rec.) | default 0.3 / 0.6 mm; smallest automatic choice 0.25 / 0.45 mm. Drill **< 0.25 mm costs extra**: 0.2 mm avoided, 0.15 mm **only when the user/design explicitly requests it** (the fab page also lists a surcharge for 0.2–0.25 mm holes with diameter < 0.45 mm) |
| PTH annular ring, 1 oz | 0.18 mm (2 L) · 0.15 mm (4 L); rec. 0.25 / 0.20 mm | recommended values |
| Via hole to track | 0.2 mm | 0.2 mm |
| PTH hole to track | 0.28 mm, rec. 0.35 mm | 0.35 mm |
| NPTH to track | 0.2 mm | 0.25 mm |
| Via hole-to-hole / pad hole-to-hole | 0.2 mm / 0.45 mm | 0.25 mm / 0.5 mm |
| Inner layer: via hole / PTH hole to copper | 0.2 mm / 0.3 mm | same |
| Copper to routed edge | ≥ 0.2 mm (edge tolerance ±0.2 mm) | **0.5 mm** (user preference: margin against milling into copper → shorts; dense designs may set less, e.g. eprom-to-kernal 0.25 mm; never below the 0.2 mm floor) |
| Copper to V-cut | ≥ 0.4 mm | 0.5 mm |
| Blind/buried vias | HDI only (laser 0.075–0.15 mm) | not used by default |

Notes:
- **Manufacturer minimums are a floor** (user decision 2026-10-30): a design value below the fab minimum (e.g. copper-to-edge 0.025 mm vs JLCPCB 0.2 mm) is raised to the minimum and flagged in the pre-flight report; design values above it are used as-is.
- **Hole sizes are discrete.** Fabs drill from a fixed tool set, so a drill size is chosen
  from an allowed list, never computed continuously (e.g. "the via that just fits"). The
  profile carries that list; the router only *selects* via sizes from it, and via diameter
  follows from drill + annular ring. Default list (generic "standard PCB drill sizes" chart
  supplied by the user; common range 0.20–1.20 mm): **0.20, 0.25, 0.30, 0.40, 0.50, 0.80,
  1.00 mm**. For routing vias the router uses **0.25 / 0.30 / 0.40 / 0.50 mm**
  (0.30 default); 0.20 is avoided and 0.15 is used only on explicit request (cost, see the via
  row above). Larger sizes are for footprint PTHs, which the router does not choose.
  All listed sizes confirmed available at JLCPCB from the user's own orders (2026-10-30);
  the full tool list may contain more sizes. Values already set in the design (netclass via sizes) are used as-is.
  Finished vs drilled hole size (plating allowance) is the fab's concern, not the router's.
- The profile should be selectable (other fabs, 2 oz, HDI) and shown in the pre-flight report
  next to every value it filled in, so the user sees which numbers came from the fab rather
  than the design.
- The profile can be written out as a `.kicad_dru` rule set so that KiCad's DRC checks the
  same values (guide rails, §4.1), instead of only the router knowing them.
- Board-setup edge clearance is **not** part of the Specctra DSN export (observed in the Topola
  test: 199 edge-clearance violations), another reason to take constraints from the project
  files rather than from DSN.

## 6. Plugin platform constraints

| Topic | Fact | Impact on feasibility |
|---|---|---|
| SWIG `pcbnew` API | Deprecated since 9.0, removal planned in 11.0 | Not a long-term basis. |
| IPC API (KiCad 9/10) | Needs a running PCB editor; no headless mode until KiCad 11; no plot/export | Router runs as a GUI action; batch use goes through files + `kicad-cli`. |
| Separate process | IPC plugins run out-of-process | Long computations don't freeze KiCad; API calls can time out while KiCad is busy. |
| Dependencies | Per-plugin virtualenv; `requirements.txt` installed **from wheels only** (no compiling) | numpy/shapely fine; a native accelerator (Rust/C++) is only possible if wheels are published for every OS/arch/Python. Licence must be GPL-compatible (CGAL GPL ok; Shewchuk's Triangle not). |
| Interactivity | No hook into KiCad's move/drag tools | TopoR's live "flexible" re-shaping is not achievable; a "re-flow after move" command is. |
| Specctra DSN/SES (Freerouting) | DSN export writes existing arcs as straight chords; Freerouting emits no arcs | Cannot combine with Freerouting via DSN without losing arcs; existing curved routing becomes wrong obstacles. |

## 7. Verdict for the KiCad side

Feasible. KiCad can store, edit and verify everything a TopoR-style router produces. The two
real constraints are (1) **no rule-engine access** — the plugin must approximate clearances
conservatively and rely on `kicad-cli` DRC — and (2) **no live interaction**, so
"flexible" routing becomes batch re-flow.
